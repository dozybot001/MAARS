Architecture boundaries

MAARS is easier to reason about when every layer has one job. The runtime controls flow. Codex does execution. The session store is the source of truth.

Runtime model

The old Docker execution tool path is intentionally retired. Docker can still be used, but only as a sandbox provider under Codex.

Runtime

Python decides control flow

Stage routing, iteration stopping, task scheduling, retries, and verification are deterministic application responsibilities.

Executor

Codex performs work

Codex receives one atomic task, runs commands, edits files in its workspace, and returns schema-constrained JSON.

Sandbox

Provider is pluggable

Local mode is the default. Docker mode wraps the same Codex command in a configured container image.

Configuration for a real run

Minimum configuration is intentionally small. Use local Codex first; switch to Docker provider only when you need stronger external isolation or a pinned runtime image.

Local Codex provider

MAARS_OPENAI_API_KEY=...
MAARS_OPENAI_MODEL=gpt-5.5
MAARS_CODEX_BIN=codex
MAARS_CODEX_MODEL=gpt-5.5
MAARS_CODEX_REASONING_EFFORT=high
MAARS_CODEX_SANDBOX=workspace-write
MAARS_CODEX_SANDBOX_PROVIDER=local

Best default for development. Codex uses its normal local auth and MAARS creates one workspace per task.

Docker Codex provider

MAARS_CODEX_SANDBOX_PROVIDER=docker
MAARS_CODEX_DOCKER_IMAGE=maars-codex:latest
MAARS_CODEX_DOCKER_BIN=docker
MAARS_CODEX_DOCKER_CODEX_BIN=codex
MAARS_CODEX_DOCKER_GPUS=all

The image must contain Codex CLI and experiment dependencies. In GPU environments, pass through GPUs explicitly.
